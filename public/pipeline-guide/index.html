0 · Orientation

Two generations, one thesis

Everything in this repo's tools/ exists because the first attempt at building an MPSC question bank was fast, cheap to write, and quietly wrong. The second attempt is slower to write and almost boring to run — and that's the point.

Gen 1 — mpsc-question-bank

Shape: crawl the whole site, throw every PDF at an LLM, ship whatever comes back.

  • 3,715 source PDFs scraped from mpsc.mizoram.gov.in
  • 77,751 questions extracted (69,778 MCQ, 7,973 descriptive) via mpsc_extract_with_oauth.py
  • 11,458 MCQ shipped with answerIndex: -1 — no resolved answer at all
  • Of 3,997 disputed answers reviewed, only 13 traced to a real answer key; 3,660 were model-inferred guesses
  • A separate, earlier OCR pipeline that fed the mpsc-state-tax-officer bank silently dropped ~280 questions across five sittings — multi-column pages mis-split, one option field swallowing the next several questions whole, with no numbering gap to reveal it because ids were re-indexed q001…qN per paper

Gen 2 — india-study-map/tools

Shape: read the text layer directly wherever one exists, escalate to OCR or vision only when measurement proves it's necessary, and verify every output against the source.

  • Narrow, deterministic parsers per sitting (parse2025.py, parse_native.py) — no OCR, no model, when a text layer exists
  • 1,092 of 1,100 option orders verified against the source PDF, 0 mismatches (validate.py) — the other 8 are figure-based with no text options to check
  • apply.py refuses to write the generated .ts file at all if any invariant fails
  • AI is used deliberately and narrowly: solving genuinely unkeyed questions, tagging to a syllabus taxonomy, classifying study mode — always behind an export/validate sandwich, never as the extractor itself
The thesis this whole guide is organized around: the model was removed from the extraction step because extraction never needed judgement. Reading a PDF's own text layer, splitting it into questions, and matching option markers is a deterministic string problem — regex and a state machine solve it exactly, every time, byte-for-byte reproducibly. The places AI stayed (§6) are the places that genuinely require judgement: answering a question with no key, deciding which syllabus leaf a question belongs to, guessing how an unmarked question should be studied. Every AI step in Gen 2 is wrapped in something that checks its work; no step in Gen 1 was.

2 · Getting the PDFs

Web scraping concepts

Two scrapers exist in mpsc-question-bank/tools/, and the second one exists because the first one's core assumption — that crawling finds structure — was wrong for this particular site.

BFS with a work queue, and why it failed here

mpsc_pdf_scraper.py keeps a plain list as its frontier and pops from the front:

list.pop(0) removes and returns the first element — combined with to_visit.append(link) further down, this makes to_visit a FIFO queue: pages are visited in the order they were discovered, one full "ring" of the site at a time, which is exactly what breadth-first search means. (It's an O(n) pop on a Python list, which is fine at a few thousand pages and would matter at a few million — see §8 for the general version of that lesson.)

BFS is the right algorithm for finding everything reachable from a start page. It is the wrong algorithm when the site has no locality — and this one doesn't:

Why BFS failed here: every page on mpsc.mizoram.gov.in shares the same global navigation menu, so a BFS crawl starting from any single page eventually visits the entire site regardless of where it started — there's no such thing as "the pages near old question papers." The rewrite (mpsc_pdf_scraper_examination.py) throws BFS away entirely and visits a fixed, hand-curated list of category pages instead.

URL hygiene: urljoin, fragment stripping, domain guards, Content-Type

  • urljoin(url, href) resolves a relative link ("../foo.pdf", "/page/x") against the page it was found on into an absolute URL. Without it, half the links on any real site are unusable.
  • .split("#")[0] strips the fragment (#section-2). Two URLs differing only by fragment are the same page/file — leaving fragments in would make visited and pdfs think they're different resources and re-crawl or re-download for no reason.
  • The domain guard (urlparse(link).netloc not in ("", DOMAIN)) keeps the crawl from wandering off-site the moment a page links to, say, a government portal or a social-media share link.
  • Content-Type check — before even parsing a page for links, the crawler confirms it got HTML back: if "text/html" not in resp.headers.get("Content-Type", ""): continue (line 113). Without it, a PDF or image response would be handed to BeautifulSoup and either crash or silently parse garbage.

Politeness, idempotence, and safe filenames

  • Politeness delay — time.sleep(DELAY) with DELAY = 1.0 between every request (mpsc_pdf_scraper.py:42, mpsc_pdf_scraper_examination.py:39). One second of courtesy costs nothing against a few thousand pages and is the difference between "polite crawler" and "getting IP-banned by a government server."
  • Idempotent re-runs — before downloading, the scraper checks if os.path.exists(path) and skips (lines 144–147). Re-running the whole script after a crash or a network blip costs nothing for files already on disk.
  • Path-traversal-safe filenames — link text becomes a filename, and link text is untrusted input. clean_title() strips exactly the characters that would let a title escape its directory or corrupt a path:

Stripping / and \ specifically matters: without a path separator in the string, a malicious or merely weird title like "../../etc/passwd" can't turn into a directory traversal — it becomes one harmless space-separated filename instead.

Provenance-based categorisation

Every general category (Answer_Keys, Results, ...) is matched by keyword against the link's title and filename. Old question papers can't be, because their titles carry no keyword at all — "Forestry Paper-I" says nothing about being an old exam paper. So they're routed by which page they were found on instead:

Why this matters: this is the same principle that later bites the scraper in §7's failure museum — when the identifying information lives in the context a document appears in rather than in the document's own name, any pipeline that only ever looks at the name/title is guaranteed to misfile something. Here the fix was applied proactively; in the Computer Operator case (§7) it wasn't, and cost real coverage.
3 · The PDF toolchain

pdftotext, pdftoppm, pdfminer, tesseract

Four tools, four different jobs. Knowing which one a given PDF needs — and proving it with a measurement instead of guessing — is most of what "PDF extraction" turns out to mean in practice.

pdftotext — reading the text layer

A "text layer" is the actual sequence of Unicode characters, with positions, that the PDF's content stream draws as glyphs — as opposed to a bitmap image of what text looks like. Every PDF produced by a word processor or LaTeX has one; every PDF made by scanning a printed page does not (it's a photograph, however page-shaped). pdftotext (part of poppler-utils) reads that layer directly — no OCR, no guessing, exact.

-layout tells pdftotext to try to preserve the visual layout (columns, whitespace, alignment) rather than emitting a raw reading-order stream. It's the right choice for a single-column exam paper — and the wrong choice for a two-column options layout, which is exactly why practice-hub-build/extract.py abandons it for pdfminer (see below). The trailing "-" tells poppler to write to stdout instead of a file, which is what lets subprocess.run(capture_output=True) capture it directly.

pdftoppm -r <dpi> -png — rasterising to images

When there's no text layer to read (a scan) or you need to see something the text layer can't represent (a highlight, a diagram), you render the page to a bitmap. DPI (dots per inch) sets how many pixels represent each inch of the physical page — 150dpi is legible for OCR on a clean scan; 400dpi is what a 1-bit fax-compressed scan needs before its glyphs are recoverable at all.

pdfminer — per-character coordinates

pdftotext -layout reconstructs a 2-D page into a 1-D stream of lines by guessing at columns from whitespace gaps — a heuristic that works until it doesn't. practice-hub-build/extract.py needs exact per-character x/y coordinates because its source booklets set MCQ options in two columns, and -layout's column reconstruction interleaves them ambiguously:

With coordinates in hand, the script builds its own line grouping by clustering characters on shared baselines (build_lines(), §5), which is a strictly more powerful and controllable approach than trusting poppler's guess — at the cost of writing that grouping logic yourself.

tesseract — what OCR actually does, and its page-segmentation modes

OCR (optical character recognition) takes a bitmap and predicts which characters it depicts — it is fundamentally a guess, informed by a trained model of glyph shapes, not a lookup. That's the whole reason a text layer is preferable whenever one exists: it's ground truth, not a prediction.

--psm N (page segmentation mode) tells tesseract what kind of layout to expect before it even starts recognising characters — get this wrong and it segments correctly-shaped text into nonsense regions.

4 · Python concepts, taught from the real code

The heart of the guide

Every card below: the plain-English idea, a tiny toy example, then the actual line from this codebase, then why it had to be there. This is the material worth being fluent in before the interview.

1. The re module

re.compile() pre-builds a pattern once so it can be reused without re-parsing the regex string every call. match() anchors at the start of the string only; search() looks anywhere; fullmatch() requires the whole string to match. finditer() yields every non-overlapping match as an iterator (lazy — doesn't build a list up front). Named groups ((?P<name>...)) let you pull a submatch by name instead of a fragile positional index. Raw strings (r"...") stop Python from interpreting backslashes before the regex engine ever sees them — without r, "\d" is passed to re as the two characters \ and d only by luck (Python leaves unrecognised escapes alone), but "\n" would silently become a real newline before re ever sees the pattern.

Real code — alternation, anchoring, a named-lookahead trick

This single pattern absorbs seven different printed variants of a "Directions" header (see §7) using alternation (-|–|—|to|&), an optional group ((?:...)?) for the range, and re.IGNORECASE because the same word appears as both "Direction" and "Directions". Anchoring with ^ and $ matters here specifically because without it, re.search would happily match "Directions" appearing mid-sentence inside an option's own text.

And the zero-width lookahead, used to tell where a broken glyph starts without consuming the letter after it:

(?=[a-z]) asserts "followed by a lowercase letter" without including that letter in the match — so fix_glyphs() can inspect text[i+1] itself to decide capital Ṭ vs lowercase ṭ (word-initial vs mid-word) while the match span stays exactly one character wide.

2. Finite state machines: the counter-guarded parser

This is the single most important idea in the whole codebase. A finite state machine processes a stream one token at a time, keeping a small amount of state, and deciding what to do next purely from (current state, current token) — no lookahead, no backtracking, no re-scanning. split_questions() is exactly this: its entire state is one integer, want — the question number it is prepared to start next — plus whatever question is currently open.

Why the counter guard matters: a naive parser would split on any line matching ^\d+\. and instantly break on "In 1935, the Government of India Act..." or a numbered list item inside a stem. Requiring int(m.group(1)) == want means the parser only ever starts a new question when it sees exactly the number it's expecting next — a stray "1935." can never be mistaken for question 1935, because want will never reach that value in a 50-question paper. This is the same idea practice-hub-build/extract.py uses under the name expect (line 419), needed for the identical reason: numbered statement lists inside a question ("Consider the following: 1. ... 2. ...") would otherwise restart the question counter on every page.

3. Monotonic / ascending-run scanning

Given a list of candidate matches that should occur in a fixed order (a, then b, then c, then d), the safe way to find the real sequence is to walk the candidates in document order and only accept the next one if it continues the expected letter — rejecting anything else as noise, rather than trusting positional or count-based heuristics.

Why: a stem that reads "...as in (a) above..." contains a real-looking option marker that is not an option. Scanning for a strictly ascending run means that marker is simply skipped — want is still "a" at that point only if it's genuinely the first one; once (a) has been consumed, only a literal (b) can extend the run, so an in-text "(a)" appearing after the real options never gets mistaken for a fifth marker. The identical pattern reappears in practice-hub-build/extract.py (line 545, guarding against "Both (a) and (b) are correct" quoting an earlier option) and in parse2025.py's parse_block().

4. Offset arithmetic: slicing spans between matches

Once you have an ordered list of match objects, the text between match k and match k+1 is body[hits[k].end():hits[k+1].start()] — and the last span runs to len(body) since there's no following match to bound it.

The stem is everything before the first option marker; each option is everything between the end of its own marker and the start of the next one (or the end of the text, for the last option). extract.py's find_option_markers + option-slicing loop (line 549–551) does the same thing at the character level rather than the regex-match level, because there the markers come from three adjacent LTChar objects rather than a single regex match.

5. Two-pointer / monotonic cursor scanning

To check that a sequence of items appears in order inside a larger text — without letting an early false match derail the rest — advance a single cursor forward through the haystack, searching only ahead of where you last found something. This is a two-pointer / monotonic-cursor technique: one pointer walks the needle list, the other only ever moves forward through the haystack.

Why the cursor has to move forward only: the bug this replaced searched the entire document for each option's text independently, with no memory of where the previous option was found. "None of the above" is common enough to appear hundreds of questions before the one actually being checked — an independent whole-document search finds that earlier occurrence and reports a reordering that never happened. Anchoring on the question's own stem and only ever searching forward from the cursor makes "found behind the cursor" mean something real: this exact question's own option text, appearing before another option that should have come after it.

6. unicodedata: NFKD decomposition and canonical "squash" forms

Unicode allows the same visual character to be represented multiple ways — an accented letter can be one composed codepoint or a base letter plus a separate combining accent mark. unicodedata.normalize("NFKD", s) decomposes every character into base + combining marks; filtering out anything unicodedata.combining() reports as a combining mark strips the accents while keeping the base letters. Combined with stripping everything that isn't alphanumeric and lowercasing, this builds a "squash" form: two strings that a human would call "the same" collapse to identical squashed strings even if their punctuation, case, or accent encoding differ.

merge_native.py defines the identical function for the identical reason (line 184–187): every text-based matching operation in this codebase — order verification, answer carry-over by option text, duplicate-option detection — runs on squash()'d strings so that "(a) Sāza" and "a Saza" and "A. Saza." all compare equal.

7. difflib.SequenceMatcher — fuzzy text matching, and its false positives

SequenceMatcher implements the Ratcliff–Obershelp algorithm: it finds the longest matching contiguous block between two sequences, then recurses on what's left on either side, and .ratio() turns the total matched length into a similarity score from 0 to 1. It's the right tool for "is this the same question, reworded or re-OCR'd slightly differently" — and the wrong tool to trust blindly, because short or generic text produces high-looking ratios against things that aren't actually the same.

The threshold is a judgement call, and it's imperfect on purpose-documented terms: merge.py uses 0.75, merge_native.py uses 0.78. Even at 0.78, a handful of short, generic stems fuzzy-matched an unrelated question elsewhere in the bank and inherited its topic — confirmed by inspecting the actual content, two ids needed a manual override (TOPIC_OVERRIDES, merge_native.py:212–215) because neither was actually an English-class question despite scoring high enough to match one. A similarity score is evidence, not proof.

8. subprocess.run — shelling out on purpose

capture_output=True captures stdout/stderr instead of letting them hit the terminal; text=True decodes bytes to str automatically; check=True raises CalledProcessError on a non-zero exit instead of failing silently; timeout=N kills a hung subprocess instead of blocking forever.

Why shelling out to poppler beats a pure-Python PDF library here: pdftotext and pdftoppm are mature, C-based, and handle the enormous variety of malformed real-world PDFs (including the 1-bit CCITTFax scans from §3) that a pure-Python library would need to reimplement from scratch. The cost is a process-spawn per call and losing Python-level exceptions in favour of exit codes — which check=True converts back into a normal Python exception anyway.

9. Generators and yield

A function containing yield is a generator: calling it doesn't run the body, it returns an iterator that runs the body up to the next yield each time you ask it for a value. This matters when producing all the values at once would be wasteful or premature — here, a page's characters are needed one page at a time by the caller, not all pages preloaded into one giant list.

The caller (extract()) writes for pno, chars in enumerate(page_chars(pdf)): — a completely ordinary for loop that has no idea it's driving a generator rather than iterating a list. That transparency is the whole appeal: you get lazy, one-page-at-a-time evaluation without the calling code looking any different.

10. collections.defaultdict, and sets for dedupe/membership

defaultdict(list) means indexing a missing key auto-creates an empty list instead of raising KeyError — turning a three-line "check, create-if-absent, append" pattern into one line. Sets give O(1) average membership tests and automatic deduplication, which is exactly what "have I seen this before" needs.

11. Dict-driven dispatch tables, and the danger of a silent default

A dict mapping id/key → outcome is a clean way to express "look this specific thing up in a table" — until the table is incomplete and the lookup falls back to a default. That default silently absorbs everything not explicitly listed, and nothing about running the code tells you how much fell through.

The 521-of-530 story: OVERRIDES is a per-id lookup, hand-built by reading the 235 questions that existed in the bucket when this script was written. Every sitting added afterward that produced a gs1_history question had no entry in OVERRIDES, so it silently fell through to "gs1_history_modern" — by the time anyone noticed, 521 of 530 history questions had piled into that one default bucket, 73 of which weren't history at all (whole current-affairs sections misclassified). The fix wasn't a smarter heuristic — it was making the fallback loud: the successor script, retag_history_modern.py, reports stragglers instead of guessing a bucket for them.

12. json round-tripping as the interchange format

Every stage boundary in this pipeline is a JSON file on disk — parse writes one, validate reads it, merge reads it and writes another, apply reads that and emits TypeScript. That's a deliberate architectural choice: any stage can be re-run independently, inspected by eye, or diffed against a previous run, because the interchange format is plain, greppable text rather than an in-memory object that only exists while one process is running.

indent=1 keeps the file diffable and human-readable without the size bloat of larger indents across thousands of records. ensure_ascii=False writes actual UTF-8 characters (Mizo diacritics, ₹, °) instead of escaping every non-ASCII codepoint as \uXXXX — which would make the file technically correct but unreadable and un-diffable to a human.

13. pathlib vs os.path

Both manipulate filesystem paths; pathlib.Path is the newer, object-oriented API (Path("a") / "b" instead of os.path.join("a", "b"), .exists() as a method instead of a free function). This codebase uses both, split roughly by when each script was written and what it needs:

Neither is wrong; Path composes more readably with / and gives you .glob()/.read_text() as methods, while os.path is what you reach for by muscle memory in a codebase that started before you'd normalize on one style.

14. tempfile.TemporaryDirectory as a context manager

A context manager (with ... as ...:) guarantees cleanup runs even if the block raises. tempfile.TemporaryDirectory() creates a scratch directory on entry and recursively deletes it on exit — bounding disk usage automatically instead of relying on the programmer to remember to clean up (or a cron job to do it later).

Rendering every page of every PDF in a 3,715-file corpus to PNG would consume enormous disk if the renders were kept around — the docstring for this exact script says as much: "Page images are deleted right after OCR so disk use stays bounded." The context manager makes that true by construction rather than by discipline.

15. hashlib.sha1 for content-addressed filenames

Hashing a piece of content (or an identifying string) into a fixed-length hex digest gives you a filename that's deterministic (the same input always produces the same name — so re-running is idempotent and automatically deduplicates) and collision-resistant enough for this purpose, without needing a counter or a database to hand out ids.

The Gen-1 README documents the same trick at corpus scale: full-page renders under images/page-renders/ are named sha1("<pdf_path>::<page>")[:20], and a question's figureGroupId is that same hash — so two questions that share a page automatically share a group id with zero coordination between them.

16. base64 for sending images to an API

HTTP JSON payloads are text; raw binary image bytes aren't valid JSON string content. Base64 encodes arbitrary bytes into an ASCII-safe alphabet so a PNG can travel inside a JSON string field, at the cost of about 33% size inflation.

17. argparse subcommand/flag design

Several scripts here share one shape: --export writes a batch of work for a human or agent to fill in; --merge reads the filled batches back, validates them, and writes the final output. Flags rather than positional subcommands keep the scripts simple while still making the two-phase, resumable workflow explicit at the call site.

The identical --export/--merge shape appears in system-manager-build/solve.py, system-manager-build/tagging.py, and system-analyst-build/classify.py — see §6 for why this specific shape (never letting the filled-in step write the real output directly) is the load-bearing part.

18. Exponential backoff with a cap, honouring retry-after

When a server says "too many requests," the naive response is a fixed sleep-and-retry; a better one doubles the wait each failed attempt (capped, so it doesn't grow unboundedly) and — when the server tells you exactly how long to wait — trusts that number over your own guess.

min(20 * (2 ** (attempt - 1)), 300) is the classic shape: 20s, 40s, 80s, 160s, then capped at 300s — never sleeping for hours even after many failures. But when the server's own retry-after header is long enough to signal a sustained limit rather than a burst (MAX_SLEEP_BEFORE_SWITCH), the code doesn't sleep for it at all — it rotates to a different account instead. See §6 for why that distinction (burst vs. sustained) is the actual cost-control decision.

19. Idempotence and byte-for-byte reproducible output

An idempotent operation produces the same result no matter how many times you run it. For a data pipeline, that means: re-running the whole chain on unchanged inputs should regenerate exactly the same output file, byte for byte — which is what lets you treat the generated .ts file as disposable and the scripts as the real source of truth.

This isn't accidental — every stage is written to check what already exists before acting: merge.py's carry-over logic reads the current bank rather than assuming a blank slate, solve.py --export skips ids already present in staged/solved.json unless --redo is passed, and tagging.py --export skips ids already in tags.json unless --all is passed. Idempotence is what makes a multi-stage pipeline safe to re-run after a partial failure instead of terrifying.

5 · Image & geometry concepts

Where pixels become facts

This section is entirely about practice-hub-build/extract.py and system-analyst-build/read_scanned_key_table.py — the two places this codebase has to reason about a PDF as a 2-D image rather than a stream of characters.

PDF space vs. raster space, and the SCALE conversion

A PDF's own coordinate system measures in points (72 per inch), with the origin at the page's bottom-left corner and y increasing upward — the same convention as ordinary Cartesian geometry. A rendered raster image (a PNG from pdftoppm) has its origin at the top-left, with y increasing downward — the same convention as almost every image format. Converting a PDF-space bounding box into pixel coordinates on the rendered PNG needs two things: scale by dots-per-inch over points-per-inch, and flip the y-axis.

The same bounding box in both coordinate systems. Higher y in PDF space means further from the bottom; higher y in raster space means further from the top.

Note y0 is computed from bbox[3] (the box's top in PDF space, i.e. the larger y) and y1 from bbox[1] (the box's bottom) — the flip inverts which edge is "min" and which is "max," so getting this backwards silently samples the wrong rectangle on the page.

PIL pixel access and Chebyshev colour distance

Image.load() returns a pixel-access object indexable as px[x, y], giving an (R, G, B) tuple for an RGB image. To decide "is this pixel the highlight colour," you can't require an exact match — antialiasing blends the highlight colour with its background at every edge, so real highlight pixels come out in a whole neighbourhood of similar colours, not one exact triple.

Requiring every channel to be within COLOUR_TOL of the target independently is a Chebyshev (L∞) distance test — the maximum single-channel difference must be small, rather than bounding the combined (Euclidean) difference across all three channels. It's simpler to compute and, for "is this basically the same colour," behaves sensibly: a pixel that's exactly right on R and G but far off on B should fail, and L∞ catches that; a Euclidean bound could let one badly-off channel hide behind two good ones.

Coverage as a confidence signal, and the widest-gap threshold that failed

coverage() returns hit / tot — the fraction of a marker's pixels that read as the highlight colour. That fraction isn't just a yes/no signal; its distance from the decision threshold doubles as a confidence measure, which is why anything landing within AMBIGUOUS_BAND (0.10) of the threshold gets reported for a human to look at instead of silently resolved.

Picking the threshold itself is the interesting part. The obvious approach — sort all observed coverage values and cut at the widest gap — sounds principled and is subtly wrong:

SI Statistics Paper II's real coverage distribution. The widest gap (0.232, between 0.436 and 0.204) is wider than the gap protecting Q28's real but faint highlight (0.204, between 0.204 and 0.0) — so cutting at the widest gap discards a genuine mark.

The fix: instead of optimising a property of the histogram (the widest empty gap), optimise the structural prior you actually know is true — every MCQ has exactly one highlighted option. Score every candidate cut by how many questions it leaves with exactly one option above threshold, and take the best-scoring cut. This is a data-derived threshold that encodes domain knowledge instead of a generic statistical heuristic.

Text-anchored sampling vs. blob clustering — a rejected alternative

The docstring documents an approach that was tried and abandoned, which is worth reading as a worked example of "sounds reasonable, fails in practice":

Blob clustering needs a padding parameter to rejoin a highlight fragmented by antialiasing — and any padding loose enough to do that reliably is also loose enough to accidentally merge two separate, vertically-adjacent options' highlight regions into one blob. Anchoring on the text (which you already know the position of from the character stream) sidesteps the whole problem: there's no blob to accidentally merge, because you're measuring a fixed, independently-known region per option rather than discovering regions from the pixels themselves.

Geometric table reading: derive structure from darkness, not from OCR digits

read_scanned_key_table.py reads a 100-row, 4-block bordered answer-key table where OCR reading the whole table as text produces garbage (a "field of pipe characters," 63 tokens for 200 cells) and, worse, misreads the question numbers themselves (7 → "z", 12 → "i2", 72 → "i"). Its fix: never let OCR determine position — only ever let it read one already-known cell's content.

dark_profile counts, for every row (or column), how many pixels are dark — a horizontal table rule shows up as a row where nearly every pixel is dark; a horizontal band of question text does not. bands() finds contiguous runs above that darkness threshold and returns their midpoints — the table's actual gridlines, found from the image itself rather than assumed at hardcoded coordinates (an earlier, hardcoded-x-range version silently lost 41 cells from two of the four column blocks because the guessed edge overshot).

The core idea: the question number comes from bi * 25 + ri + 1 — the cell's position in the grid — never from anything OCR reads. Tesseract is only ever asked "what single letter is in this one cell" (via --psm 7 plus an ABCD whitelist), a much easier and more constrained question than "read this whole table," and a misread letter can at worst give a wrong answer for one already-correctly-numbered question — it can never shift every subsequent answer by one row, the way a misread number would.

Private-use-area font demapping

Some PDFs embed a Symbol-like font for maths where the glyphs are visually operators (+, −, ≤, √) but are mapped, in the font's internal encoding, to Unicode's Private Use Area (U+E000–U+F8FF) — codepoints Unicode deliberately leaves undefined for exactly this kind of vendor-specific reuse. The text layer faithfully reports the codepoint the font uses, which is meaningless without knowing that specific font's private mapping.

Without this table, x² − kx − 3 = 0 extracts as x−kx−3=0 — actually worse, since the minus signs themselves are also PUA codepoints in the same font; a question that depended on the equation extracts as unsolvable nonsense with no error raised anywhere.

Superscript/subscript detection by size and baseline offset — emitted in runs

A superscript is typographically smaller and sits above the surrounding text's baseline; a subscript is smaller and sits below it. Detecting this per character and classifying it is only half the job — the other half is emitting consecutive same-kind characters as one run, not one at a time, or a multi-character ordinal like "38th" degrades into "38^t^h" with each raised letter marked up independently, oblivious to its neighbour.

The median glyph size and median baseline y across the whole line are used as the "normal" reference (a small, cheap way to be robust to lines that are entirely a different font size) — then a character only counts as super/subscript if it's both smaller and off-baseline in the matching direction. Runs are found by advancing a second index j forward while the classification stays the same, then emitting that whole run through the superscript/subscript Unicode lookup table at once — the same "classify then run-length group" pattern as §4's ascending-run scanning, applied to a different problem.

Vector-glyph reconstruction: the ₹ sign as a stroked path

Not every visible mark on a PDF page is a text character at all — some are vector paths (lines, curves, filled shapes) drawn directly by the content stream. These booklets draw the ₹ (rupee) sign as a small filled path rather than a font glyph, so it is completely invisible to anything that only reads the character stream — "₹800 per month" extracts as "800 per month" with the currency silently gone.

The fix wraps the detected path in an object that quacks like a character (get_text() returns the glyph it represents) so it can flow through the rest of the pipeline — line grouping, rendering — exactly like any real LTChar, with no special-casing needed downstream. The size filter (4 < w < 9 and 7 < h < 11) is a rupee-sign-shaped bounding box, snapped onto the baseline of nearby real text since the raw path geometry sits a couple of points too high to group correctly on its own.

Underline detection as thin filled rects near a baseline

An underline in a PDF's content stream is just another filled rectangle — very short vertically, spanning some horizontal range at roughly the height of the text baseline. Distinguishing "this is an underline rule" from "this is some other filled shape" is a matter of aspect-ratio and position, not semantics the PDF format actually encodes.

Why this matters: for a "part of speech" or "identify the underlined phrase" question, the underline is the question — README.md's own schema convention marks the underlined span with **word** so the UI can render it distinctly, and without detecting it Q51 would read "Identify the underlined phrase" with nothing underlined anywhere in the extracted text.

The cost-control architecture

  • Free regex gate before any spend. mpsc_classify.py exists purely to answer "is this even worth sending to a model" — MCQ vs. descriptive vs. non-paper vs. answer key — using nothing but pdftotext and pattern matching. Its own docstring states the reasoning: "this script's job is to say which files those are before anyone pays for a single token."
  • Escalation ladder, evidence-gated at every rung. Text layer → tesseract → vision, and each rung only fires when the previous one is measured to fail — see the exact measurement table in §3 (58/75, 42/75, 32–33/75 across psm modes, none acceptable, hence vision). The rule is: measure before escalating to a paid model, never assume.
  • Per-PDF conditional vision. Even inside the Gen-1 model-based extractor, most PDFs go through as text-only — vision is attached only when the page text itself signals a diagram is present:
  • Checkpoint files that distinguish deterministic failure from transient failure. A PDF that produced zero questions, or couldn't extract text at all, is recorded in ATTEMPTED_FILE and never retried — that outcome won't change on a re-run. A PDF that raised an exception mid-call (rate limit, network blip) is deliberately not recorded there, so the next run retries it automatically:
  • OAuth subscription tokens vs. credit-billed API keys. Per-account OAuth tokens (obtained via claude setup-token) bill against that account's weekly subscription quota; keys from console.anthropic.com are billed per token against a credit balance. The Gen-1 README is explicit that credit-billed keys are "what was burning money before" — the OAuth-token extractor exists specifically to move extraction volume onto quota instead of a metered bill.
  • 429 handling that classifies the limit by its duration, and rotates rather than sleeps for hours. See the full backoff mechanics in §4 concept 18 — the short version: a short retry-after is honoured with a sleep; a long one signals a sustained/weekly cap, and the code switches accounts instead of blocking.
  • Sharding for safe concurrency. --shard-id gives each concurrent process its own checkpoint/attempted/batch-file namespace and, combined with a static --worklist JSON, guarantees two shards never claim the same PDF — concurrency without a shared-state race.

The methodology: the export/merge sandwich

Every place a model answers, tags, or classifies something in this codebase follows the same shape, and the shape is the actual safety mechanism — not the model's competence.

The model never writes the shipped output. It only ever fills a todo file that a separate, deterministic step validates before anything is merged in.

Notice what's being checked: not "does this look plausible" but exact membership in a known-valid set (valid, built from the taxonomy file). A model that returns a paraphrased or slightly-off leaf name is rejected outright, with a helpful case-mismatch hint, rather than accepted because it's "close enough."

The rule pre-pass: a cross-check, not a classifier

classify.py's rule_hint() deliberately does not decide anything — it only flags the cases a narrow regex is confident about, and its output is diffed against what the model produced, never substituted for it.

The framing in that docstring is worth internalising for the interview: "a pipeline that agreed with itself would prove nothing." Two independently-derived opinions that happen to agree is real evidence; one process checking its own output never is.

Blind cross-validation: solve without seeing the existing answer

solve.py exists to verify 308 questions that arrived with an answer but no explanation and no official key behind them. The design is explicit about the failure mode it avoids: a solver shown "the bank says (b)" tends to rationalise (b), whether or not (b) is actually right.

When the bank has no answer to diff against at all (Election Dec-2019 Paper II: all 74 answers -1), a lone solve would ship its own self-assessed confidence completely unchecked — so a second, independent blind pass stands in as the comparison:

Why different models specifically: if the same model is wrong about something systematically — a common misconception, a training-data gap — running it twice reproduces the same wrong answer twice, and "agreement" would look identical to genuine corroboration while meaning nothing. Two different models are far less likely to share the same blind spot, so their agreement is actual evidence and their disagreement is an honest signal of real uncertainty (both answers are then shown to the reader, capped at medium confidence, rather than one being silently picked).
7 · The failure museum

What broke, why it was invisible, and the transferable lesson

These are the specific, real incidents this codebase's defenses (validate.py, invariant gates, count assertions) exist to prevent from happening again.

1. 280 questions lost, with no numbering gap to reveal it

What broke: an OCR pipeline mis-split multi-column scans; one option field swallowed the next several questions whole (e.g. ...2016-gs-iii-q040 held questions 47, 48 and 49 inside its own option (b)).

Why it was invisible: question ids were re-indexed q001…qN per paper. A paper that should have 100 questions but silently has 91 still numbers them q001–q091 — there's no gap, no error, nothing to notice. Measured loss: ~280 questions across five sittings, plus 68 surviving questions visibly broken.

The fix: re-parse from the source PDF's text layer directly and compare the resulting count against the paper's known, independently-verified expected question count — expected is a parameter to every parse function in bank-rebuild/, and a mismatch is printed loudly rather than silently accepted.

Transferable lesson: a count that can silently drift (re-indexed ids) hides data loss that a count anchored to independent ground truth (the paper's own numbering, verified once by hand) cannot. Assert on counts against something you didn't derive from the same broken process.

2. Option-order silent corruption

What broke: nothing has to "break" for this one — it's a standing risk. Every answer key, every UI letter (a)-(d), and answerIndex itself are all positional. If an option set is silently reordered anywhere in the pipeline, a previously-correct answer becomes wrong with zero visible symptom: the data still looks completely well-formed.

The fix: validate.py's check_order() (§4) re-reads the source PDF and confirms every option appears in the stored order, anchored to that question's own stem. 1,092 of 1,100 checked, 0 mismatches.

Transferable lesson: "the data is well-formed" and "the data is correct" are different claims, and a schema or type check only ever proves the first one. Positional data needs a check against the one thing it's positional relative to — here, the literal order of characters in the original document.

3. A case-sensitive end-marker glued a section onto Q50's last option

What broke: the GS-II paper prints its section boundary as "SECTION - II"; GS-III prints the same boundary as "Section - II" — different capitalisation, same exam sitting.

Why it was invisible: a case-sensitive end-marker match against GS-III's mixed-case heading would simply never fire, so the "end of MCQ section" boundary is never found and the parser keeps consuming lines — the entire following descriptive section reads as if it were the last option of question 50.

The fix: match the end marker case-insensitively (re.IGNORECASE), with a comment recording exactly why: parse2025.py:17-19, "Getting this wrong silently glues the whole descriptive section onto the last option of Q50."

Transferable lesson: when the same logical marker is documented to vary between two sibling papers of the same exam sitting, assume it varies in more ways than you've already seen, and default to the more permissive match unless you have a specific reason not to.

4. Unmatched "Directions" header variants leaking into the previous question's option (d)

What broke: MPSC prints a "Directions" header above a run of questions in seven different textual forms across different papers — different punctuation, "for" vs "to", a comma instead of a colon, or no separator between the header word and the range.

Why it was invisible: any variant not matched by the regex is treated as ordinary body text — the parser has no concept of "unrecognised header," only "this line belongs to whatever question is currently open." So the header text is silently appended onto the last option of the preceding question, and the option still reads as plausible prose.

The fix: one regex with enough optional groups and alternation to absorb all seven forms (§4, concept 1) — found incrementally, each variant added only after a real paper proved it existed.

Transferable lesson: a "matches the format I've seen" regex quietly becomes "matches the formats I happened to sample" — real corpora have more variants than your test set, and the failure mode (silent absorption into an adjacent field) gives you no signal that a variant was missed.

5. Flush-vs-discard: dropping cur deleted the preceding question silently

What broke: when the parser hits a "Directions" header, the question it was building has to be closed off before starting to collect the direction text. An early version of this logic simply reset the in-progress question variable without saving it first.

Why it was invisible: the question being discarded was, by construction, complete and well-formed right up until the moment it was thrown away — there's no partial-state, no malformed record, just one fewer question in the output with no trace it ever existed.

Transferable lesson: "close the current record" and "discard the current record" look identical in a diff of the state-machine's variables (both end with cur = None) — the only difference is one line, blocks.append(cur), and it has to run before the reset, every single time state transitions away from "collecting a question."

6. The widest-gap threshold discarding a real faint highlight on Q28

Covered in full in §5. The short version: splitting a coverage distribution at its widest empty gap is a property of that specific histogram, not of what a highlight actually is — and on SI Statistics Paper II, the widest gap sat on the wrong side of a genuine but faintly-drawn mark, discarding it. The fix optimised the actual structural invariant (exactly one highlight per question) instead of a shape in the data.

Transferable lesson: when you know a strong structural fact about your data ("exactly one of these is true per group"), a threshold chosen to satisfy that fact directly will usually beat a threshold chosen by a generic property of the distribution (widest gap, biggest cluster, etc.).

7. retag_history.py's silent default bucket

Covered in full in §4, concept 11. The short version: a per-id lookup table with a fallback default absorbed every question added after the table was written — 521 of 530 history questions ended up in the default bucket, 73 of which weren't history at all.

Transferable lesson: a dict-with-a-default is safe only as long as the dict is known to be exhaustive at every call site, forever. The moment new data can arrive that the dict wasn't built to cover, the default needs to be loud (raise, or report as a straggler) rather than quiet.

8. The scraper took anchor text when the identifying text was in the sibling table cell

What broke: MPSC's listing pages put the post name (e.g. "Computer Operator") in one table cell and the paper's download link in the next cell. The scraper's category/title logic only ever looked at the link's own anchor text and filename — so five real Computer Operator sittings saved to disk as Paper-II(AH&Vety).pdf, 2.Technical Paper-I.pdf, 3.Technical Paper-II.pdf, with the string "Computer Operator" appearing nowhere in the filename, the paperId, or index.csv.

Why it was invisible: an inventory built by grepping the bank for "Computer Operator" — a completely reasonable way to audit coverage — found exactly four papers and reported that as the whole set. A keyword search genuinely cannot find a paper whose identifying information was never captured as a keyword anywhere. Worse, two different source URLs both saved as the identical filename 2.Technical Paper-I.pdf (a MIMER Laboratory Technician paper and a MIMER Computer Operator paper), and one silently overwrote the other on disk — that Computer Operator paper is still missing from the local corpus today.

The fix: stop trusting the filename/anchor text as identity; read the actual listing table's structure (post name in the sibling cell) to determine what a paper is for. A too-loose header guard downstream (matching on the employer, "MIZORAM INSTITUTE OF MEDICAL EDUCATION AND RESEARCH," rather than the specific post) then imported 75 Laboratory Technician anatomy questions labelled as Computer Operator questions — caught not by the pipeline but by two tagging agents independently refusing to tag anatomy content against a computing syllabus.

Transferable lesson: when a document's identity lives in its surrounding context rather than in the document itself, any process that only inspects the document (or its filename) in isolation will misfile it — and a downstream audit built on the same kind of keyword search will confirm the miscount rather than catch it, because it's making the identical assumption.

9. Global option search reporting 169 phantom reorderings

Covered in full in §4, concept 5. The short version: an early version of the option-order checker searched the whole document independently for each option's text. Generic short options ("None of the above") occur dozens or hundreds of questions apart, so the independent search found an earlier, unrelated occurrence and reported it as evidence of reordering — 169 times, none of them real.

Transferable lesson: "does this text appear in the document" is a different, much weaker claim than "does this text appear where I expect it, relative to what I already found." Anchoring and scanning forward from a known-good position turns a noisy signal into a reliable one.

10. TS2590: union type too complex to represent

What broke: a single 1,300+-element BankQuestion[] array literal, where BankQuestion is itself a discriminated union with a wide subject union inside it, overflowed TypeScript's type checker — tsc refused to compile with "Expression produces a union type that is too complex to represent."

Why it happens: checking one giant object-literal expression against a union type asks the compiler to test every element against every arm of the union in one pass; the cost grows with the size of the single expression, not with the total amount of code.

The fix: two independent mitigations, both necessary. Split the one big literal into 200-element chunks concatenated with spread syntax (...questions0, ...questions1, ...) — each chunk is small enough to type-check on its own, and the runtime result is byte-identical to one big array. Separately, stamp an explicit type discriminant on every record so tsc doesn't have to test each literal against both arms of the union to figure out which one it is.

Transferable lesson: a type checker's cost model isn't always "total lines of code" — sometimes it's "size of the single expression it has to reason about in one pass." When you hit a checker resource limit, ask whether the code can be restructured into more, smaller units that mean the same thing at runtime, rather than fighting the checker directly.

Walk me through the project. ✓ reviewed

Two generations of the same problem: build a searchable question bank from MPSC's past exam papers. Gen 1 (mpsc-question-bank) crawled the whole site and threw every PDF at an LLM — 3,715 PDFs, 77,751 questions, but 11,458 with no resolved answer and a separate OCR pipeline that silently dropped ~280 questions with no visible symptom. Gen 2 (india-study-map/tools) is narrower and deterministic: read the PDF's own text layer directly with regex and a small state machine wherever possible, escalate to OCR or vision only when measurement proves the text layer route fails, and verify every output — option order, question counts, invariants — against the source before it ships. The thesis: extraction is a deterministic string problem and never needed a model; the places AI stayed are the ones that genuinely need judgement (solving unkeyed questions, tagging, classification), and every one of those is wrapped in a validation step that can reject its output.

What was the hardest bug to track down?

The highlight-detection threshold in practice-hub-build/extract.py. Splitting the sorted coverage values at the widest gap in the histogram sounds like the obviously correct, principled approach — and it silently discarded a real, faintly-drawn highlight on Q28 of an SI Statistics paper, because the spread within the "marked" population happened to exceed the gap protecting that one faint mark. It's a hard bug specifically because the wrong approach isn't naive — it's a reasonable statistical idea that fails on a specific, real distribution shape. The fix required abandoning "find structure in the histogram" for "optimise directly for the structural fact I already know is true" (every MCQ has exactly one highlighted option).

How do you know the extraction is correct?

Not by trusting the parser's own output — by checking it against the source PDF independently. validate.py's check_order() re-reads each source PDF and confirms every stored option appears in the paper in the same order, anchored to that question's own stem and scanned strictly forward (a two-pointer technique, chosen specifically because an earlier whole-document search produced 169 phantom reorderings from generic option text). Currently 1,092 of 1,100 checked, 0 mismatches. Separately, hygiene() checks for the specific defect signatures the old pipeline left behind — leftover option-letter prefixes, swallowed neighbouring questions, duplicated options, page furniture. And apply.py refuses to even write the generated file if any rebuilt-paper invariant fails.

Why not just use AI for everything? It would be so much faster to build.

Because extraction — splitting a known text layer into questions and options — never needed judgement, and using a model for a deterministic problem trades exactness for a probabilistic guess with no reason to. That trade is exactly what produced Gen 1's ~280 silently-lost questions and 11,458 unanswered ones. AI earns its place only where the task is genuinely ambiguous or requires judgement a regex can't encode — answering a question no key exists for, deciding which syllabus leaf a question belongs to — and even there, it's never trusted alone: every AI step sits inside an export/merge sandwich where a deterministic step validates its output before anything ships, or a cross-check (a second model, a rule pre-pass, a diff against a known answer) before its confidence is accepted at face value.

Tell me about a mistake you made.

I imported 75 Laboratory Technician anatomy questions and shipped them labelled as Computer Operator questions, and didn't notice. The header guard I'd written to confirm a PDF belonged to the right exam only checked for "MIZORAM INSTITUTE OF MEDICAL EDUCATION AND RESEARCH" — true of every MIMER paper regardless of which post it was for, not specific enough to distinguish Computer Operator from Laboratory Technician. What actually caught it wasn't the pipeline — it was two independent tagging agents refusing to tag bone-types-and-Ziehl-Neelsen-staining content against a computing syllabus and tracing it back to source. The fix made the header check a list that pins the specific post, not just the employer, with a negative test proving it rejects the Laboratory Technician paper.

How did you control cost?

Several layers, applied in order. First, a completely free regex/text-stats classifier decides which PDFs are even worth sending to a model at all, before a single token is spent. Second, an escalation ladder — text layer, then self-hosted tesseract, then a paid vision call — where each rung only fires after the previous one is measured to fail on that specific document class (the render_pages.py measurement table: 58/75, 42/75, down to 32-33/75 across psm modes, all short of the 75 actually on the page). Third, vision is attached per-PDF only when the page text itself signals a diagram is present, via a regex (DIAGRAM_SIGNAL_RE), rather than rendering every page's images unconditionally. Fourth, OAuth subscription tokens bill against a weekly quota rather than a metered credit balance. Fifth, 429 responses are classified by their retry-after duration — short waits are honoured, but a long one signals a sustained limit and triggers an account switch instead of blocking for hours.

Where would this break at 100× scale?

Three specific places, each with a known fix. coverage()'s pixel loop in extract.py is a pure-Python nested loop over every pixel in a bounding box — fine for a handful of booklets, but it should become a vectorised NumPy comparison (np.all(np.abs(arr - target) <= tol, axis=-1).mean()) at real scale. merge_native.py's answer-carry-over is SequenceMatcher run against every old question for every new one — O(new × old) — and needs a blocking key (a cheap token or length signature) to cut candidates down before the expensive fuzzy comparison runs. And derive_threshold()'s gap search is O(n²) in the number of distinct coverage values (it recomputes the "how many questions have exactly one hit" count from scratch for every candidate cut) — a sorted sweep that maintains an incremental running count as the cut moves would make it linear.
